## Day 1: backend (pre-built starter kit)

- Data model and access rules designed up front, written as PocketBase migrations (schema as code).
- Rules verified with an automated API test acting as each demo user: new hires see only their own data, can't promote themselves, can't edit or reassign others' progress, and there's no public sign-up. All checks passed.
- Design choice: no progress row = "not started," which keeps seed data and writes small.
- Design choice: app-level `coordinator` role kept separate from PocketBase superusers (the admin UI owner).

- Tested the access rules myself with curl as Priya: she sees only her own data, her attempt to make herself coordinator got a 404, and editing her own name worked. The server enforces this, not the UI.

**Step 0 security review: what changed** (one migration per fix; the applied ones were never edited)
- **#2** New hires could tick off IT and manager tasks, which also cleared their own "Blocked" flag. Now they can only flag those tasks as blocked or add a note. The strict version would have stopped them reporting a blocker at all, so it chose this middle option.
- **#3** New hires could backdate `completed_at`. Rules can't stamp a value and there's no server code, so it now has to be within ±1 day of server time.
- **#4** New hires could edit their own `team` and `manager_name`, which show on the coordinator's roster. Now coordinator-only.
- **#6** Every new hire could see every cohort (future dates and locations). Now only their own.
- **#7** After a cohort move, stale progress rows stayed editable and could flag the person as blocked forever. Progress is now scoped to the current cohort, and CLAUDE.md requires queries to filter by `task.cohort`.
- **#1** The repo is public and the seed password is in it. A stranger could create their own coordinator account and lock out the demo. Fix: a private password on the deployed instance, plus TODO.md and a CLAUDE.md instruction so I don't forget.
- **#8, #9, #10** Documented, not changed: `week` quirks, the rollback reopening sign-up (it doesn't survive a restart), and password resets via the admin UI (a coordinator reset rule would be an account-takeover tool).

**Where the AI was wrong, and how it was caught**
- **#8:** it said a task with no `week` would drop out of the "Behind" count. Testing showed PocketBase stores it as 0, so it actually counts as pre-work. It corrected itself.
- **#7:** testing turned up a side effect it hadn't predicted. The #2 rule was already partly blocking stale rows, because the rule's check on a task respects the tasks collection's own access rule. We made that explicit in the rules.
- **#9:** it first overstated the risk. Testing showed `serve` re-applies every migration on startup, so a rolled-back state can't persist.
- Its first rule test returned a 404 that looked like a pass but had hit the wrong row (an IT task). It noticed and re-ran the test on the right row.

**Step 3b regression tests: what they caught**
- **A real bug in step 3.** If a coordinator opened someone's side panel while a cohort was still loading, the panel became disconnected: changes stopped refreshing it and Esc couldn't close it. The manual test in step 3 had passed by luck of timing; the automated test hit it on the first run. Fixed by hiding the roster during loads and ignoring outdated responses. This is the clearest case for having the tests.
- **Proving the tests can fail.** It put back the original, looser progress rule and 7 API checks failed, each naming the protection that was lost. It broke the roster sort and the dashboard test failed, showing the wrong order. A suite that has only ever passed proves nothing.
- **A false alarm in its own deploy check.** The first version checked that test pages return 404 on the live site, but PocketBase answers every unknown path with the app page (200), so it would always have failed. It now checks the page content.
- **Design choice:** a "denied" check passes only if the server refused the request because of an access rule.

**Step 3c code review: what it found** (each fix in its own commit; tests passed before every commit)
1. **Quick consecutive saves were cancelled (bug).** The PocketBase SDK cancels a pending request when another with the same method and URL starts, and every "create progress row" shares one URL. Ticking two tasks quickly showed an error and reverted a checkbox, but the server had saved both, so re-ticking hit the duplicate-row check and the user was stuck until reload. In the coordinator panel the dropdown just froze. Fix: saves opt out of auto-cancel. New UI tests failed on the old code, then passed.
2. **Tests could write to someone else's database (bug).** If anything held port 8099, the test server failed to start but the readiness check succeeded against the other server: "68 passed" while creating users in that database. Fix: refuse to run if the port is taken.
3. **Unlimited password guessing (deployment risk).** PocketBase ships with rate limiting off; 30 wrong passwords in a row were all answered normally. Fix: a migration turns it on (2 sign-ins per 3s per IP), the login screen says "Too many sign-in attempts", the tests prove it's on before switching it off on throwaway servers, and the deploy check verifies it on the live site. Open question for deploy: PocketHost's proxy may make every visitor look like one IP (TODO.md).
4. **CDN-loaded SDK had no integrity check (supply-chain risk).** The SDK holds the login token, so a tampered CDN file could take over any account. Fix: an integrity hash (a tampered hash makes Chrome refuse the file) and a Content-Security-Policy allowing scripts only from this site and the pinned SDK.
- **Checked and fine:** no `innerHTML` anywhere in the app, all filters parameterised, new hires can't change their own email or `verified` flag, every rule covered by tests. A request that failed because the test sent malformed data fails the test instead of counting as a denial.

## Day 3: deploy

- **Live URL:** https://liftoff-mvp.pockethost.io (deployed 2026-10-16; demo passwords are private, not the repo's)
- **How:** uploaded `pb_migrations/` and `pb_public/` over SFTP (no Node needed, so no `phio`), restarted so the migrations ran, replaced all five demo passwords in the admin UI, then `tests/check-deploy.sh` passed 13 of 13 and my browser smoke test passed as each demo user.
- **Surprises:**
  - **SSH key name.** I saved the key as `~/.ssh/pockethost`, so SFTP's default lookup never tried it ("Permission denied"). The AI checked the key, passphrase, and agent before guessing, then pointed SFTP at the file.
  - **PocketHost puts its own files in the instance** (a defaults migration and two hooks). We listed the folders before uploading and left those alone.
  - **Cloudflare in front of PocketHost.** Without configuration, PocketBase saw every visitor as `172.17.0.1`, so the whole internet would share one sign-in limit. I set the trusted header to `CF-Connecting-IP`. The AI then tested spoofing on the live site: a faked `CF-Connecting-IP` is blocked by Cloudflare itself (error 1000), and a faked `X-Forwarded-For` is ignored by the rate limit. Its first spoof test returned 403s instead of the expected 429s, and it checked who sent them before drawing a conclusion.
  - **Admin UI details:** the password field hides behind a "change password" switch, and Application URL defaults to `http://localhost:8090`.
  - **Cloudflare cached the old CSS and JS.** After the agenda deploy, the live dashboard showed the agenda as an unstyled bullet list, while local looked fine. Cloudflare caches `styles.css` and `app.js` for 4 hours but not `index.html`, so visitors got new HTML with old styling and script. The AI's deploy check had passed because it added its own cache-busting `?v=` to every request, which proved the server had the right files, not that visitors got them. It owned that, then fixed both halves: `index.html` now loads the files with a content-hash `?v=` (kept current by `tests/asset-versions.sh`, which the tests enforce), and `check-deploy.sh` now follows the live page's own links through the cache. The new check failed on the broken site before the fix and passed after.
  - **The December surprise.** While listing local-vs-hosted differences, the AI spotted that from Nov 2 the dashboard would open on the empty December cohort. It's fixed now: the dashboard defaults to a cohort with new hires, with date-fixed tests that fail under the old rule. The fix went live by re-uploading `app.js`; static files update without a restart.
